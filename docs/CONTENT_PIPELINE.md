# Конвейер контента: как добавляются и чистятся вопросы

Раздел для мейнтейнера. Ученику и человеку, который просто запускает проект,
он не нужен — им хватит README.

> ⚠️ **Главное правило.** `id` вопроса — это ключ, по которому хранится
> прогресс: в `progress/<user_id>.json` у бота, в SRS на устройствах и в базе
> синхронизации. Однажды выданный id принадлежит своему вопросу навсегда.
> Скрипты сборки банка это соблюдают сами, а сторож в CI ловит нарушения.
> Подробности — в разделе «Иммутабельность id» внизу.

## Формат вопроса

`questions.json` (UTF-8), массив объектов:

```json
{
  "id": "vhf-019",
  "topic": "VHF / SRC",
  "q": "Текст вопроса?",
  "options": ["Вариант 1", "Вариант 2", "Вариант 3", "Вариант 4"],
  "answer": 0,
  "expl": "Пояснение к правильному ответу.",
  "why": ["Почему вариант 1 верен", "Почему 2 нет", "Почему 3 нет", "Почему 4 нет"],
  "ref": "МППСС-72, Правило 5"
}
```

- `answer` — индекс правильного варианта (0 = первый);
- `expl` — общий разбор, показывается под вариантами;
- `why[i]` — почему конкретный вариант верен или нет; в Mini App показывается
  только у ошибочно выбранного варианта, чтобы не дублировать `expl`;
- `ref` — источник; он же питает `docs/SOURCES.md`.

## Вариант A — вручную

Добавить объект в массив `questions.json`. Подходит для одного-двух вопросов.
После правки обязательно прогнать `python run_audit.py`.

## Вариант B — импорт CSV

```csv
topic,question,A,B,C,D,answer,explanation
VHF / SRC,Какой канал для DSC?,70,16,13,72,A,DSC использует канал 70.
```

```bash
python import_csv.py путь/к/новым_вопросам.csv
```

`answer` — буква `A/B/C/D` или индекс. Вопросы с уже существующим текстом
пропускаются.

> ⚠️ Известное расхождение: `import_csv.py` и `merge_dedup.py` трактуют поле
> `answer` **по-разному** (эвристика 1-based против 0-based). Один и тот же CSV,
> прочитанный двумя скриптами, может дать разные правильные ответы. Пока это не
> исправлено, после импорта выборочно сверяйте ответы глазами.

## Вариант C — слияние нескольких баз с дедупликацией

Положить все `.csv` в `sources/` и запустить:

```bash
python merge_dedup.py                       # объединить + записать questions.json + отчёт
python merge_dedup.py --dry-run             # только анализ и отчёт, без записи
python merge_dedup.py --collapse-semantic   # ещё и свернуть смысловые дубли
```

Три уровня проверки дубликатов:

1. **Точные дубли** — одинаковый текст после нормализации регистра, пунктуации
   и пробелов. Удаляются автоматически; пояснение подтягивается из лучшего
   варианта.
2. **Близкие по тексту** — схожесть ≥ 0.88 по `SequenceMatcher`. Только
   помечаются в отчёте.
3. **Смысловые дубли** — один и тот же факт разными словами. Группируются по
   «подписи факта»: номер правила МППСС, комбинация огней, паттерн гудков,
   кардинальный знак, определяемый термин, числа в навигационной задаче.
   «Что требует Rule 5?» и «Что капитан обязан вести всегда — зрением и слухом?»
   получают одну подпись `colreg:rule5-lookout`, хотя текст разный.

Отдельно отчёт показывает **конфликты** — когда один вопрос в разных базах имеет
*разный правильный ответ*. Это всегда ручная проверка.

Полный отчёт — в `dedup_report.txt`. По умолчанию смысловые дубли только
помечаются; с `--collapse-semantic` из группы остаётся один лучший вопрос.

## Иммутабельность id

Принятая модель (владелец, 31.07.2026; доведена в волне C, 13.11.2026):
**id — это имя вопроса, а не хеш его текста и не позиция в файле.**

| Что происходит | Можно? |
|---|---|
| Исправить опечатку в тексте, вариантах или пояснении под тем же id | да |
| Добавить новый вопрос с новым id | да |
| Неизменённый вопрос (текст + картинка) получил другой id | **нет** — ошибка CI |
| Два вопроса с одним id | **нет** — ошибка CI |
| Сменить правильный ответ (`answer`) при тех же вариантах | только через `scripts/answer_fixes.json` |
| Удалить вопрос | пока предупреждение; его id больше никому не выдаётся |

Хеш-id от текста отвергнут: он запретил бы правку опечаток (исправил букву —
вопрос «стал новым», прогресс потерян).

### Как это обеспечено

**Скрипты сборки** (`merge_dedup.py`, `integrate_generated.py`, `import_csv.py`)
работают через общий модуль `bank_ids.py`:

- существующий вопрос выходит из скрипта **тем же словарём**: тот же id, все
  поля, включая те, о которых скрипт не знает (`why`, `ref`, `difficulty`, …);
- новый вопрос получает `q-NNN` с номером **больше любого, который когда-либо
  был в банке** (по всей истории `questions.json` в git). Освободившийся id
  удалённого вопроса не переиспользуется: он мог остаться в чьём-то прогрессе.
  Старые префиксы `colreg-`, `iala-`, `vhf-src-` остаются у своих вопросов,
  новых с ними не выдаётся.

**Сторож** `scripts/check_question_id_stability.py` (CI, джоба `id-stability`)
сравнивает банки с базовой ревизией:

- ключ соответствия — текст + `image`. В Sternik десятки вопросов с одинаковым
  текстом («Przedstawiony znak oznacza:») различаются только картинкой;
  перестановка картинок между ними — это тоже перенос id;
- смена `answer` при неизменных `options` — ошибка, если в
  `scripts/answer_fixes.json` нет записи `"<id>": "<текст нового правильного
  варианта>"`. Так ловится съехавший индекс при пересборке, а осознанное
  исправление ключа остаётся возможным и видно в диффе.

Проверить локально: `python scripts/check_question_id_stability.py --base HEAD`.
Тесты модуля и сторожа: `python test_content_pipeline.py`.

### Польские банки

`webapp/questions_zeglarz.json` (`zj-*`) и `webapp/questions_sternik.json`
(`st-*`) — это экзаменационные листы PZŻ, их не пересобирают, а правят руками.
Каждое поле — «польский\nрусский». `run_audit.py` (пункт 12) проверяет
структуру, mojibake, формат «PL\nRU», приклеенный перевод соседнего варианта
(«… Б. …») и картинки. Потерянные польские диакритики (`sie` вместо `się`)
выводятся предупреждением со списком id: сам лист содержит опечатки, полная
вычитка — ручная работа.

## После любого изменения банка

```bash
python run_audit.py                 # пред-релизный чек-лист (все три банка)
python scripts/check_question_id_stability.py --base HEAD   # id не уехали
python webapp/build_quiz_data.py    # регенерация данных Mini App (ISSA)
python webapp/build_zeglarz_data.py # … и польских банков, если их правили
python webapp/build_sternik_data.py
node webapp/_quiz_check.mjs         # валидность данных и лимиты payload
node webapp/_licenses_check.mjs
```

CI проверяет, что `webapp/*_data.js` не отстали от исходников: если забыть
регенерацию, сборка упадёт.
